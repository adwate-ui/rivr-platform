# Security review, October 2026

Date: 27 Oct 2026 · Task: #112 (tech plan "Release gates", hardening) · Code reviewed: `origin/integration` at 6f53e49d, plus this task's fixes.

## How it was done

- **The live schema, by query.** A locally reset database (all 149 migrations and the seed), queried as `postgres` for what the code cannot hide: row-level security, grants, view options, function settings, storage policies, the Realtime publication and cron jobs. The results are below.
- **The code, in five read-only slices.** The `security-reviewer` agent read each slice against `.claude/rules/security.md`, `.claude/rules/database.md` and the decisions they cite:
  1. row-level security policies, views and column grants;
  2. security-definer functions and the RPC surface;
  3. Edge Functions;
  4. `packages/adapters`;
  5. exports (decisions 0190 and 0232).
- **Checked before fixing.** Every finding fixed here was first confirmed in the code, and each fix has a test that fails without it.
- **Severity.** Critical means exploitable now with serious harm. High is money or identity at risk through one person's misuse. Medium is real but bounded, or needs a mistake to happen. Low is defence in depth. Info is noted, nothing to do.

## What the schema shows (clean)

- Every `public` table has row-level security, and no policy grants to `anon` or `public`.
- The only policy that is literally `true` is the global `feature` catalogue, read by signed-in users.
- All 876 functions in `public` and `private` pin `search_path=""`.
- `public` has 268 functions:
  - the 245 that signed-in users can call are all security invoker;
  - their permission checks live in `private` definer functions;
  - `anon` can call none of them.
- `anon` reads only the 11 `public_*` views. Each one leaves out the practice venue and holds no personal data except P4 (#493).
- All 15 public views are `security_invoker`, and each private `*_rows` function behind them filters by the caller.
- `private` is not exposed through the API (`api.schemas` is `public` and `graphql_public`), and GraphQL is not installed.
- The 23 public functions for the service role alone (KYC vendor results, payouts, device pairing, outbox claims) are not executable by signed-in users.
- Storage:
  - `kyc` and `expense-receipts` are private;
  - `kyc` has no policy, so photos are reached only through `kyc-image-url`'s short signed links;
  - `brand` is public and takes PNG only;
  - the policies allow inserts only, into the caller's own venue folder, with no update or delete.
- Realtime publishes `control_state`, `member`, `member_feature_override` and `tier_feature`, and its topics are venue-scoped.
- Dynamic SQL quotes every identifier and literal (`%I`/`%L`), in the practice reset and in the export archive.
- Edge Functions:
  - the Send SMS hook checks Standard Webhooks signatures;
  - the scheduler's secret is compared in constant time, and an empty secret refuses every call;
  - no function logs personal data, and errors are fixed codes.
- Adapters:
  - Cashfree is signed on every call, secrets go in headers, replies are parsed by Zod, and amounts convert exactly from paise;
  - payouts are idempotent per attempt key;
  - KYC and payouts stay closed while their secrets are missing;
  - the practice venue always gets the fakes.

Also noted, as follow-ups that do not block launch:
- The `aml.settings_changed` alert has no words in `@rivr/i18n` `alerts`, so it says "something needs your attention" (#105). This review's new alert has words.
- The Settings screen still offers admins the keys only a super admin may change (the AML keys and 0213's). The database refuses them, but the screen says "Your role does not change settings", and a reason shorter than three characters shows the generic "unavailable" message. The screen should mark these keys and ask for a reason of three characters or more.
- `kyc_review_queue` still lists checks the reviewer may not decide (their own, or a member they changed). The database refuses them on Approve. The in-person list already leaves those out.

## Checks only staging or the owner can make, before launch

1. **Realtime privacy.** As a member, subscribe to `control_state` and `member_feature_override` changes, and engage a member freeze on that member. The payloads have no `reason` or `lift_reason`. If they do, publish column lists (`alter publication supabase_realtime ...`).
2. **The client's address.** On staging, `select private.request_ip()` through the API returns the caller's address from `cf-connecting-ip` (decision 0022).
3. **Phone changes.** Make the staging check in #496, then build #502.
4. **Cashfree's environment.** After the first release that carries this change, the production secrets page shows `CASHFREE_ENVIRONMENT` with the digest of `production`. Check it with `printf production | sha256sum`.
5. **Auth's dashboard settings** (`docs/runbooks/ci-and-release.md`): CAPTCHA on, rate limits set, only `public` and `graphql_public` exposed. The code cannot show these.
