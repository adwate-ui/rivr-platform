# 0513: Phones and the hidden money modules held by the database

Date: 9 Nov 2026 · From the 180-day audit of 8 Nov (F-001, F-042, F-022, F-038); the owner approved fixing every finding before launch.

- **Members' numbers.** Signed-in callers read every `member` column but `phone`. `member_search` and `member_record` give the full number only to staff who may change it (`members.change_phone`, the super admins), as the Members list already does; to other staff they give none, not the last four the Members list shows, because no screen draws a number from either. Other staff find a member by the number's last four digits, which they see, or all ten, never by other runs of digits that would spell it out; the at-the-club identity list matches the same way. The kill switch and an Academy booking look a member up with `member_id_for_phone`, which returns only the id.
- **Kept on purpose:** the host queue gives hosts the full number of a lapsed member, because calling them is its job.
- **Colleagues' numbers.** Signed-in callers read every `staff` column but `phone`. The Staff screen reads `venue_staff`, which gives each number to staff who manage staff (`staff.manage`). The kill switch finds a staff member with `staff_id_for_phone` (`control.engage`).
- **A new column** on either table needs its own grant. Tests 333 and 334 check that signed-in callers read every column but `phone`, so a missing grant fails there.
- **GraphQL** is not a way round the check: `pg_graphql` is installed neither on staging nor on production (read on 8 Nov).
- **Hidden money modules.** Their functions stay in the database (decision 0284: hide, don't delete). PostgREST asks `private.refuse_hidden_modules` before every request (`pgrst.db_pre_request`), which refuses `anon` and `authenticated` the listed `/rpc/` paths with 42501. The list is every function `packages/db` calls only for a hidden screen that keeps money (cage, treasury, shift close, markers and credit, withdrawals, deposits, wallet, payout and payment accounts, expenses, Tally, TDS, jackpots, shareholding), with the hidden tournaments' and Academy's money and the hidden money reports; not what live screens read (the TV's jackpot board, tournament interest, a member's Academy bookings). SQL inside the database, the service role and the pgTAP suite are untouched. A module comes back by taking its paths off the list; a new function for a hidden module goes on it.
- **One exception to schema rule 6.** The pre-request check is a private function `anon` may execute, because PostgREST runs it for the website's anonymous requests too. It only refuses; test 001 names it. Asked as a question issue (CLAUDE.md rule 9); this is the safest reading meanwhile, since without the exception there is no gate at all.
- **Not done:** a module switch per venue. Nothing turns a hidden module on today, so one list in one function is enough.
