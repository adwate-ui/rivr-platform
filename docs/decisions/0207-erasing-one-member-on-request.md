# 0207: Erasing one member's personal data on request

Date: 2026-10-27 · Task: #424 (the owner's plan of 26 Oct)

A super admin (`members.erase`, never another role) erases one member: the full name typed and a reason naming nothing of the person (no word of the name, five digits, `@` or PAN). The database refuses while anything is open (wallet cash, chips, markers, points or bonus owed, a reward to hand over, the waitlist, a tournament not finished, a waiting request, an unpaid academy booking, a freeze), then does it all in one transaction. A busted run counts until its tournament finishes, as a run in the money is paid into the wallet then.

- **Forfeit.** Points go to `venue.points_issued` and bonus to `venue.bonus_expense`, as a redemption and an expiry do. The ledger keeps one unit to a transaction, so these are two `member_erasure_forfeit` transactions, named in the one `member.erase` audit row. The open bonus grants are locked first and closed, so the expiry job never takes the bonus twice.
- **Deleted:** preferences, notification choices, limits, feature overrides, attribution, the card, feedback, KYC reviews, queued messages (only messaging consumers read the outbox), payout accounts no money record names, and the login unless staff or a device use it.
- **Anonymised:** the member row (`Erased member`, no number or login, `erased_at`; a check keeps it so), consent withdrawn, and the KYC record kept with the PAN alone where TDS was taken at the cage or on a prize (else deleted). An erased member is never checked again, and an erased record never makes a new check a duplicate.
- **Kept as they are:** the ledger, the cage, TDS, invoices as issued (with `buyer_name`), markers, payout accounts a withdrawal or deposit names (marked removed), play, breaks and freezes, and staff reasons written on those rows (a bonus's reason, a ledger memo). Readings for the CA to confirm.
- **Audit log.** The rows about the member lose names, numbers, notes, staff reasons and the KYC vendor's handle (`private.strip_erased_fields`). The guard allows exactly that one update, inside an erasure, as the database owner, for that member's rows. A row's own `reason` and `ip` columns stay.
- **A break in force** leaves a block until it ends: keyed hashes (`private.kyc_reference`) of the number and of the KYC identity (DigiLocker key, Aadhaar reference, PAN, last four Aadhaar digits with the birth date), no name. That number does not join the venue (`RVBRK`), and a KYC check matching any hash is refused (`on_break`), however it is made. The owner chose the hashes beyond the number and the identity key (#479). A nightly job drops ended blocks.
- **Practice venue** erases the same way, then captures its seed again (decision 0117), which also keeps the practice play of that moment. Nothing is sent out.
- **After a restore,** `private.reapply_member_erasures(since, member_ids)` erases again from the audit log and named ids. Running it twice changes nothing. `docs/runbooks/backups-and-restore.md` says where the ids come from.
- **The console** erases through the database itself: erasing is admin-computer work (decision 0110), which only the browser's own request may do. It then asks the `member-erase` Edge Function to remove the member's KYC folder with the service role. The database names that folder, asked as the caller, only for an erased member and an active super admin of their venue. It checks the role, not the computer, since the erasure that needed the computer is already made. So the function removes nothing else and tells no one else who was erased. The record shows any KYC files still in Storage, with Remove, after a failure or a restore.
- **Seeds.** Staging runs every seed on each deploy, so a seed's KYC row for an erased member is skipped, not refused: only a person is refused.
