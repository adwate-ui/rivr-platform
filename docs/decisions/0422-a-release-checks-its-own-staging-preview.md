# 0422: A release checks its own preview on staging, so main keeps merging

Date: 3 Nov 2026. The owner, through the parallel session: "a release shouldn't freeze main". Two releases on go-live day held every merge for 30 to 60 minutes, because each merge redeploys staging and the release checked staging itself.

- **What the release checks.** The `stage` job builds the tagged commit's five web apps against staging and puts them on each staging project's preview alias named after the tag, as `preview.yml` does per pull request: `https://release-YYYYMMDD-N.rivr-<app>-staging.pages.dev`, and the website's `https://release-YYYYMMDD-N-rivr-web-staging.<account>.workers.dev`. The website there links to that alias's player app. `e2e-staging` runs the `@staging` flows (decision 0420) against those addresses.
- **What it no longer needs.** Staging no longer has to run exactly the tagged commit. Its last deploy must be the tagged commit or a later main commit, so staging's database and functions already have the tag's migrations. Merges and staging deploys carry on while a release runs.
- **The trade-off.** The release checks the tagged apps against staging's backend as it stands, which may be ahead of the tag; production gets the tag's own backend. A later migration that breaks the tagged apps fails the release rather than passing one that would break.
- **Proof before relying on it.** The `@staging` set ran against pull request #824's preview aliases on 3 Nov: every check of the hosts passed (sign-in, console, TV, tablet, offline app, website pages). Only the two website-link checks failed, as that preview's website links to staging's player; the release's own build links to its alias.
- **Also here.** Every web build now gets `VITE_WEB_URL` (staging's or production's website, which the console's website editor previews needed and never had) and the Tag Manager container as `VITE_GTM_ID` and `PUBLIC_GTM_ID` from the variable `GTM_ID`.
