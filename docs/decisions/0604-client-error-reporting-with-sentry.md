# 0604. Client error reporting with Sentry

Issue #928, owner 15 Nov: at the trial run, 12 of 41 sign-ups stopped before the selfie and nothing reported an error. Sentry was already the stack's choice (`docs/engineering/stack.md`). Decided while building, with the owner's rulings of 15 Nov; the player app only.

- **An exception to "external calls only in outbox consumers, through `@rivr/adapters`".** A browser's error cannot wait for an outbox: the page that would write the row is the one that failed. And `@rivr/adapters` runs in Edge Functions and takes no vendor SDK. So the player app posts to Sentry itself, from `apps/player/src/features/error-reporting` and nowhere else, and its tests run the real SDK with the post kept in memory, not an adapter's fake. `@rivr/ui` and `@rivr/db` know nothing of Sentry: they hand the app a callback.
- **Off unless the build names an address.** `VITE_SENTRY_DSN` comes from the environment and is in no file. Without it (local work, unit tests, e2e, any deploy that does not set it) nothing is kept, the SDK is never fetched, the service worker does not keep it, and nothing is sent. `VITE_APP_VERSION`, when set, is sent as the release. No workflow passes either: the owner said later (15 Nov), so this lands with reporting off everywhere. Disabling the project's client key in Sentry is the instant off switch afterwards.
- **Loaded after the first paint.** The SDK (`@sentry/react`, 32 KB gzipped) is a chunk of its own. The app's own listener starts with the first module `main.tsx` imports, so an error thrown while the app starts is kept; it keeps ten at most, each with the route's pattern at that moment, until the SDK has loaded. A failure in a script shared with other screens, which a browser runs before `main.tsx`, is still not seen.
- **What is reported:** errors nothing caught, promises nothing handled, a screen that failed to draw (the router's `defaultOnCatch`), and the failures screens handle themselves: every read that fails (`read:member:42x501`), every change the server refuses (`refused:not_live`), a camera that would not start or a photo that could not be made (`camera:blocked`), the captcha (`captcha:not_loaded`) and the sign-up form's own checks, by field name (`sign_up_invalid:fullName,city`). Each is a short code made of words from the code, the database or Auth, never a typed value (`@rivr/db` `failureCode.ts`), once a visit for each code, tagged `kind: handled` and an issue of its own in Sentry. Only errors thrown from the app's own scripts under `/assets/` are sent: not a browser extension's, nor a script an in-app browser adds.
- **Sent:** the error's type and message, its stack (file, function, line), the last requests (method, address without its query string, status) and moves between screens, the page's address without its query string, the browser's user agent, and three labels: the app, the kind and the route's pattern (`/sessions/$sessionId`), plus the version as the release.
- **Never sent:** who is signed in (no user, id, name, phone or email), cookies, headers, request or response bodies, query strings, typed input, clicks, console lines, page text, screenshots or local values. No Session Replay, feedback form, tracing, logs or sessions. Each integration is named in `sentry.ts`, so one a later SDK turns on by default adds nothing.
- **Location.** The SDK tells Sentry not to keep the IP address, and the stored event has none. Sentry does store a city-level location it derives from the connection (country, region, city), never the address itself. The owner's ruling: leave it, and leave the project's settings as they are.
- **Scrubbed before it leaves** (`scrub.ts`, tested by example and through the real SDK, and again on the SDK's last hook before sending): phone numbers and any four digits or more however spaced or dashed (an Aadhaar number, a sign-in code), PANs joined or spaced, email addresses, tokens and long keys, row ids, photos written out as text, quoted words except the database's names for its own things, a row or value the database quotes back, and all the words of anything thrown that was not an error. Input is cut to 2,000 characters first, so no error's words can stall the page.
- **What no rule can tell from ordinary words:** a name in an error's own sentence, one word in single quotes, a member number under four digits, a token shorter than 32 characters. Nothing in the app puts these in an error today, and nothing made to hold a name is sent, but an error whose own words spell one out would carry it.
- **The practice venue never reports.** The member read now says whether their venue is the practice one (`useMember().isPractice`). A member of it sends nothing; signed out, or signed in and still joining, errors are sent; while a session, its member or their venue is still being read, errors wait and are sent or dropped once it is known. What remains: an app that fails before it can read who is signed in reports that failure, knowing no venue.
- **Later** (issue #1004): the production variable and workflow line; source maps; an environment name; Sentry's tunnel through our own domain, as a network that blocks Sentry's hosts, the owner's own until 15 Nov, sends nothing; the console, tablet, TVs, website and Edge Functions.
